# 从 HTML Demo 到企业级交付：Claude Code 驱动的 FDE 标准化交付方案

版本：V1.0（2026-11-04）｜定位：内部研发与交付体系建设｜第一阶段：真实客户试点

## 一、我们此前讨论得出的结论

1. **商业定位**：不是只做一个人的 FDE 外包，而是发展一家以企业 AI 落地交付为主的服务公司。初期小项目建立信任，后续提供维护、迭代服务；成功案例转化为可复制行业交付包。
2. **核心优势**：客户/老板信任、业务理解、需求拆解、迅速展示 Demo；不需要自己训练底层大模型，也不要依赖招募大量“全能 FDE”。
3. **前端获客和后端交付分离**：DC-HONEY 继续负责快速生成 HTML Demo；Claude Code 作为内部工程生产工具，负责后端、数据库、API、办公平台连接、测试与部署材料。
4. **规模化目标**：业务端可发展合作顾问和渠道，但签约必须通过集中技术评审；总部沉淀公共模板、连接器、标准、测试和人才培训；交付人员通过工具/模块放大产能。
5. **当前真实基础**：现有 Demo 仅是前端演示，尚无可靠后端或企业应用接入。因此**先交付一条真实业务闭环，不先建设大而全的交付平台**。

## 二、第一阶段产品边界

**首个样板建议：企业询盘处理 / 报价草稿**（仅作验证场景，可替换为首个付费客户的真实需求）。

员工打开企业办公软件中的应用入口（或从企业内部网页进入）→ 提交询盘表单或上传资料 → 后端保存 → AI 提取需求并生成**报价草稿** → 业务员/主管在系统中审核 → 审核通过后保存状态、向相关员工发送通知 → 全程可追踪。

- P0 必须具备：可运行页面、后端 API、数据库、账号/权限、AI 任务、人工审核、操作审计、消息通知（先选**一个**办公平台）、部署说明。
- P0 不做：自动读取所有员工私人聊天、未经授权读取组织数据、自动发出有法律效力的对外报价、复杂 ERP 双向写入、完整的工作流编排平台、三平台一次性深度支持。
- 平台审批接口各有差异：P0 先做**我们自己系统的审批流程**，办公平台只提供入口/通知；原生审批流程在后续针对具体客户需求适配。

## 三、系统架构

```text
售前：老板提出想法 → DC-HONEY 生成 HTML Demo → 客户确认功能/流程
                                     │ 导出静态文件 + 需求确认单
                                     ▼
内部研发：Claude Code + CLAUDE.md + Skills + 人工代码评审
                                     │ 基于统一项目模板实现
                                     ▼
┌──────────────────────────────────────────────────────┐
│                  企业 AI 业务应用                     │
│   原 HTML 改造的 Web/H5 页面  ───►  Node.js 后端 API │
│                                           │          │
│              ┌────────────────────────────┼───────┐  │
│              ▼                            ▼       ▼  │
│       PostgreSQL（业务记录）       AI 模型适配层 任务队列│
│                                             │        │
│       权限、审计、密钥管理、监控、限流、租户隔离        │
└─────────────────────────────┬────────────────────────┘
                              ▼
                  企业办公平台连接器接口
                  ├─ 企业微信 Adapter（P0）
                  ├─ 飞书 Adapter（按客户需要）
                  └─ 钉钉 Adapter（按客户需要）
```

**关键原则**：企业办公工具是身份、页面入口、消息通知/事件入口，**业务逻辑与数据归属独立**；换办公平台不重写核心报价逻辑。不可把三个平台包装成“完全相同”的能力，必须维护能力矩阵。

## 四、推荐技术基线（可根据已有 Demo 调整）

- Node.js + TypeScript + NestJS（模块化后端）；REST API；OpenAPI 文档。
- PostgreSQL + Prisma（业务数据、迁移与审计）；Redis + BullMQ（较长 AI 任务/重试，初期只有简单任务时可先保留接口）。
- 前端：优先保留 DC-HONEY HTML 视觉与交互；以薄适配层连接 API，必要时再重构为 React，不强制重写。
- 模型：后端独立 ModelProvider 接口，支持接入经客户允许的国内可用模型供应商；记录每次 token、失败率和成本，不把模型密钥放在 HTML。
- 开发本地环境：Docker Compose 启动数据库和相关服务；`.env.example` 提供变量名称，但绝不包含真实凭证。
- 部署：首个客户优先选择符合法务与数据要求的独立环境/隔离空间；同时预留 `tenant_id`，所有读写必须经过租户及权限校验。未来 SaaS 混合模式需额外安全评审。
- 明确区分**Claude Code（研发工具）费用**与**交付后客户使用的模型 API 费用**，不得将前者直接当作生产推理服务。

## 五、核心模块与接口合同

| 模块 | 首版实现 | 可复用资产 |
| --- | --- | --- |
| Demo 迁移 | 识别 HTML 页面、表单、静态假数据与交互；出“功能映射表”，逐个接后端 | Demo 导入 Skill / 验证脚本 |
| 用户与租户 | 企业/用户/角色、组织映射、RBAC、租户隔离 | Auth 模块、租户守卫、测试 |
| 业务工作流 | 询盘 → AI 处理 → 草稿 → 审核 → 归档；有状态机 | Workflow 模板、领域模型 |
| AI 服务 | Prompt 版本、结构化输出校验、人工审批、成本记录 | ModelProvider + PromptRegistry |
| 企业连接 | 授权、事件接收、消息发送、H5 应用入口、身份映射 | Connector 合同 + 平台 Adapter |
| 可靠性 | 幂等、重试、审计、错误告警、备份恢复 | 通用中间件、测试/监控模板 |
| 交付管理 | 需求确认、测试报告、账号/权限清单、上线与培训记录 | 标准交付文档包 |

连接器统一接口（概念合同，具体签名由 Claude Code 输出并测试）：

```ts
interface WorkspaceConnector {
  provider: 'wecom' | 'feishu' | 'dingtalk';
  capabilities(): {
    login: boolean;
    appEntry: boolean;
    sendNotification: boolean;
    receiveEvents: boolean;
    nativeApproval: boolean;
  };
  verifyAndNormalizeEvent(input: unknown, context: ConnectorContext): Promise<NormalizedEvent>;
  resolveIdentity(input: ExternalIdentity, context: ConnectorContext): Promise<InternalUserIdentity>;
  sendNotification(input: NotificationInput, context: ConnectorContext): Promise<DeliveryResult>;
  buildAppEntry(input: EntryLinkInput, context: ConnectorContext): Promise<string>;
}
```

**注意**：这是架构接口，不代表三平台已经支持所有能力。每个平台以它当前开放的 API、客户授权范围和应用类型为准。所有回调需要验证、去重、快速应答、异步处理；消息发送要有失败重试与可见记录。

建议首批 REST 端点（需身份/权限校验）：
- `POST /api/v1/inquiries`：新建询盘；
- `POST /api/v1/inquiries/:id/generate-draft`：提交生成任务；
- `GET /api/v1/quotes/:id`：查看草稿与审核状态；
- `POST /api/v1/quotes/:id/approve`：人工审核（记录审核人和版本）；
- `POST /api/v1/connectors/wecom/callback`：企业微信事件（按平台要求验签/解密）；
- `GET /api/v1/health`：健康状态。

## 六、Claude Code 内部交付组织

**人的职责不可完全交给 AI**：业务顾问确认客户需求与验收口径；技术负责人审批架构、授权方案、生产发布；交付工程师运行和评审 Claude Code 生成的代码；独立测试/安全检查把关风险。

建议 Claude Code 角色分工：
1. 需求分析 Agent：读取 Demo 和客户确认单，输出功能清单、边界与验收用例；不能自行编造业务规则。
2. 架构 Agent：数据库、权限、部署、安全与连接器设计，先出方案和风险。
3. 后端 Agent：基于模板完成 API、数据库迁移、模型适配层和任务队列。
4. Connector Agent：仅实现已选定办公平台的真实 API 适配；不能用 Mock 冒充生产接入。
5. QA/Security Agent：独立检查租户隔离、权限、提示注入、数据泄露、回调签名、依赖风险及测试覆盖。

Claude Code 机制：
- `CLAUDE.md` = 所有项目必须遵守的规则与交付约束；
- `.claude/skills/` = 重复性任务，如 Demo 导入、新平台连接、发布验收；
- Subagents = 代码阅读、专项实施或独立审查；
- Hooks/CI = 自动运行 lint、typecheck、unit/integration/e2e 测试；**不可用 Hooks 代替上线审批**。

## 七、90 天并行执行路线（不是必须限制获客）

**第 1–2 周：底座和需求评审**
- 建立代码库、`CLAUDE.md`、基本 CI、Docker Compose。
- 导入一个真实 HTML Demo，输出“页面 → API → 表/字段 → 权限 → 业务规则”映射表。
- 选定第一个付费/试点客户和办公平台，锁定 P0 验收口径。

**第 3–4 周：实际可用的业务闭环**
- 完成登录、数据库、询盘录入、AI 草稿、人工审批、日志与最小测试。
- 在测试环境用真实账户（非演示假数据）走通页面到数据库；AI 输出要校验并记录错误。

**第 5–6 周：首个办公平台接入**
- 如果客户在企业微信办公，则先做企业微信；若客户主要用飞书/钉钉，则优先对应平台。
- 完成管理员授权、身份映射、应用入口和消息通知；事件接收作为增量功能。
- 所有授权资料由企业管理员提交给安全存储，不录入对话、代码或日志。

**第 7–8 周：试点验证**
- 选择受控范围员工试用、记录效率基线、失败案例、人工审核情况与工时。
- 完成故障回滚、备份恢复演练、权限检查、验收与交接。

**第 9–12 周：可复制化 + 继续获客**
- 提取可复用模块，形成第二个客户可复用的样板仓库。
- 建立诊断单、项目难度分级、交付工作量估计、报价模板、独立验收标准。
- 按真实成交需求增加第二个平台连接器；不要为“看起来完整”一次开发三套。
- 试行外部合作工程师交付，但客户数据与核心安全权限仍由公司统一控制。

**业务可以并行跑，不必停下来等研发**：顾问持续见客户、做 Demo、卖“付费诊断”；正式签约和交期承诺必须通过总部容量、数据、技术可行性和毛利评审。

## 八、验收与扩张判断

首个项目交付成功至少意味着：
1. 真实数据经过“提交 → AI 草稿 → 审核 → 保存/通知”，不依赖演示假数据；
2. 未经授权的用户不能访问其他用户、其他企业的数据；
3. 模型出错/超时/格式不合格时有安全失败、重试或人工处理路径；
4. 回调验签和幂等、凭证存储、审计、备份/恢复经过测试；
5. 客户管理员自行完成合法授权与账户交接；
6. 有运行部署文档、测试证据和用户验收记录。

扩张指标建议**先作为经营目标，而不是已经达到的事实**：完成 3 个同类付费项目；新项目可复用的核心代码逐步提高；第二个客户不需要老板亲自写代码；单项目工时、毛利、模型成本、客户留存、故障率均可测量。只有指标稳定后再扩大渠道和交付合作伙伴规模。

## 九、风险与边界

- **不能从截图/HTML 自动推导完整业务逻辑**：客户要确认数据字段、权限、审批规则、异常情况和接口权限。
- **不同平台的接口不是完全统一**：身份、消息、回调和原生审批都有差异；缺能力时明确提示，不做虚假的“已连接”。
- **安全与合规**：遵循客户合同及中国境内适用的数据/个人信息规定；检查数据跨境、模型供应商、客户授权、日志脱敏与删除要求；生产上线需人工审批。
- **真实报价必须人工核实**：AI 负责建议与草稿，不应未经审核对外自动承诺价格或交期。
- **Claude Code 是内部研发工具**：不要未经许可代客户转售其账号或将其当作交付系统的生产运行时；客户侧 AI 调用由合规的独立模型 API 承担。
- **成本可控**：跟踪 Claude Code 开发用量、人力审核工时、模型 API token、云资源、维护工时；先计量再定价。
